Analogia rápida: o frontend é a loja (vitrines e atendentes). O backend é o estoque e o caixa. As pastas separam “quem atende o cliente” (controllers), “o mapa das ruas” (routes), “as receitas internas” (services) e “as prateleiras” (banco/Prisma).

1. Visão da raiz

smaug/
├── backend/          ← API (servidor Node/Express)
├── frontend/         ← site (React + Vite)
├── docs/             ← PDFs e HTMLs de estudo
├── DOCUMENTACAO.md   ← texto longo sobre o sistema
├── package.json      ← resto antigo na raiz (o app real está nas duas pastas)
└── .gitignore        ← o que o Git não envia (ex.: .env, node_modules)

O projeto é um monorepo simples: dois aplicativos irmãos. Você sobe o backend na porta 3000 e o frontend na 5173.

2. Pasta backend/

Para que serve esta pasta? É o servidor. Recebe pedidos HTTP do React, autentica o usuário, aplica regras de negócio e grava/lê dados no PostgreSQL. Sem o backend, a tela não tem de onde tirar os dados.

backend/package.json

Lista as bibliotecas do servidor (Express, Prisma, JWT, bcrypt, axios, cors, dotenv) e os scripts: npm run dev (nodemon), start e seed.

backend/.env

Segredos locais: URL do banco, JWT_SECRET e RAWG_API_KEY. Não vai para o GitHub.

backend/.env.example

Modelo vazio do .env, para outra pessoa saber quais variáveis criar.

backend/package-lock.json

Trava as versões exatas das dependências. Não se edita na mão.

3. Pasta backend/prisma/

Para que serve esta pasta? É o “contrato” com o banco de dados. O Prisma lê o schema, gera o client JS e aplica migrations (alterações SQL versionadas).

schema.prisma

Desenho das tabelas: User, Console, Game (incluindo isDigital), Achievement, UserAchievement e DailyQuiz. Define tipos, relações e regras como email único.

seed.js

Popula as 4 conquistas padrão (FIRST_CONSOLE, FIRST_GAME, COLLECTOR_10, QUIZ_MASTER) com upsert. Não cria usuário.

migrations/

Histórico SQL. Cada subpasta é uma mudança no banco.

migrations/20261026134636_init/migration.sql

Criação inicial de todas as tabelas.

migrations/20261111200000_add_game_is_digital/migration.sql

Adiciona a coluna isDigital na tabela Game (checkbox “versão digital”).

migrations/migration_lock.toml

Trava o provedor (PostgreSQL) para as migrations não misturarem bancos.

4. Pasta backend/src/

Para que serve esta pasta? Código-fonte da API. Tudo que “roda de verdade” no servidor (exceto Prisma/seed) mora aqui.

server.js

Ponto de entrada: carrega o .env, importa o app e faz listen na porta 3000. Não define rotas.

app.js

Monta o Express: CORS, JSON, health check GET / e encaixa cada grupo de rotas em um prefixo (/api/auth, /api/games…). Também dá require no achievementService para registrar o EventEmitter.

5. Pasta backend/src/config/

Para que serve esta pasta? Infraestrutura compartilhada. Evita criar várias conexões com o banco.

prisma.js

Cria uma instância de PrismaClient e exporta. Controllers e services importam daqui em vez de instanciar o Prisma de novo.

6. Pasta backend/src/middlewares/

Para que serve esta pasta? Funções que rodam antes do controller. No SMAUG, a principal é a autenticação: se o token for inválido, a request nem chega na lógica de consoles/jogos.

authMiddleware.js

Lê o header Authorization: Bearer …, verifica o JWT e coloca req.userId. Sem token válido responde 401.

7. Pasta backend/src/utils/

Para que serve esta pasta? Funções pequenas e reutilizáveis, sem regra de negócio pesada.

jwt.js

signToken (cria o token com validade de 7 dias) e verifyToken (valida a assinatura com JWT_SECRET).

8. Pasta backend/src/routes/

Para que serve esta pasta? É o mapa de URLs. Cada arquivo diz: “neste caminho, chame aquela função do controller”. Aqui não se valida formulário nem se grava no banco — só o encaminhamento. Quase todos aplicam authMiddleware.

authRoutes.js

POST /register, POST /login (públicas) e GET /me (protegida). Prefixo final: /api/auth.

consoleRoutes.js

CRUD de consoles: POST/GET /, GET/PUT/DELETE /:id. Prefixo: /api/consoles.

gameRoutes.js

CRUD de jogos no mesmo padrão REST. Prefixo: /api/games.

dashboardRoutes.js

Só GET /stats. Prefixo: /api/dashboard.

achievementRoutes.js

Listar conquistas, grant, grant-all, limpar e revogar. Prefixo: /api/achievements.

quizRoutes.js

GET /today, POST /submit, POST /reset (demo). Prefixo: /api/quiz.

externalGameRoutes.js

Busca e detalhes de jogos externos. GET /games/search e GET /games/:id. Prefixo: /api/external.

9. Pasta backend/src/controllers/

Para que serve esta pasta? (a que você citou como exemplo)

O controller é o “atendente do guichê”. Ele:
  • recebe req (body, params, query, e o userId do middleware);
  • valida se faltou campo;
  • chama Prisma e/ou um service;
  • devolve res com JSON e o código HTTP certo (200, 201, 400…).
Ele não deveria ser um amontoado infinito de regras reaproveitáveis — essas vão para services/. Cada arquivo abaixo cuida de um assunto da API.

authController.js

Cadastro (hash bcrypt + JWT), login (compara senha) e me (dados do usuário logado, sem senha).

consoleController.js

CRUD de consoles do usuário. Filtra por fabricante/geração/mídia. No create dispara conquistas. No delete apaga jogos ligados em transação.

gameController.js

CRUD de jogos. Normaliza gêneros (array), tenta vincular consoleId se o usuário já tem aquele console, grava isDigital e dispara conquistas no create.

dashboardController.js

Agrega estatísticas: totais, soma de preços, jogos por console e por gênero.

achievementController.js

Lista conquistas com flag unlocked. Também tem ações de demo/admin: conceder uma, conceder todas, limpar e revogar — devolvendo unlockedAchievements para o toast.

quizController.js

Busca o quiz do dia (escondendo o gabarito se ainda não respondeu), corrige as 5 respostas, libera QUIZ_MASTER se gabaritar, e reseta o quiz para demonstração.

externalGameController.js

Orquestra a busca de jogos: catálogo local de consoles primeiro, depois RAWG, e se a RAWG cair, Steam. No detalhe, escolhe a fonte pelo id (local-…, steam-… ou RAWG).

10. Pasta backend/src/services/

Para que serve esta pasta? Regras de negócio e integrações que vários controllers podem usar. Um service não precisa saber de Express (req/res). Ele recebe dados, faz o trabalho e devolve um resultado.

achievementService.js

Concede conquista só se o usuário ainda não tem. Funções processConsoleCreated, processGameCreated e processQuizMaster. Também registra um EventEmitter (Observer).

quizService.js

Banco grande de perguntas (~70). Sorteia 5 evitando as dos quizzes recentes do mesmo usuário (inclusive no reset de demo).

rawgService.js

Cliente HTTP da RAWG: busca e detalhes, limpa HTML da sinopse. Timeout curto para não travar a tela se a API externa estiver lenta.

steamService.js

Plano B de busca/detalhe na Steam Store (melhor para jogos de PC).

11. Pasta backend/src/data/

Para que serve esta pasta? Dados estáticos do próprio SMAUG — não vêm de API externa nem do PostgreSQL. Usado para o autocomplete de clássicos de console quando a RAWG falha.

consoleGames.js

Catálogo local (Zelda, Mario, Halo, Chrono Trigger, etc.) com nome, console, gêneros, sinopse. Exporta searchLocalConsoleGames e getLocalConsoleGame.

12. Pasta frontend/

Para que serve esta pasta? É o site que o usuário vê. React desenha as telas; Vite empacota e sobe o servidor de desenvolvimento na porta 5173.

package.json

Dependências da interface: React 19, React Router, Axios, Tailwind 3, Recharts, lucide-react, Vite.

vite.config.js

Liga o plugin React e fixa a porta 5173.

tailwind.config.js

Diz ao Tailwind quais arquivos varrer para gerar as classes CSS.

postcss.config.js

Liga Tailwind + Autoprefixer no pipeline de CSS.

index.html

Página HTML mínima com <div id="root">. O React “entra” nesse div.

13. Pasta frontend/src/

Para que serve esta pasta? Todo o código da interface. Convenção típica de app React: um arquivo de entrada, o App com rotas, e pastas por tipo (páginas, componentes, contextos).

main.jsx

createRoot no #root, envolve App com StrictMode e importa o CSS global.

index.css

Diretivas @tailwind e fundo escuro padrão do body.

App.jsx

Árvore de providers (AuthProvider + AchievementToastProvider) e o React Router: login/register públicos; dashboard, consoles, games, achievements e quiz privados.

14. Pasta frontend/src/pages/

Para que serve esta pasta? Uma tela inteira por rota. Página = layout daquela URL (quase sempre com Navbar). Formulários grandes reutilizáveis ficam em components/ (modais).

Login.jsx

Formulário email/senha. Chama login do AuthContext e redireciona se já estiver autenticado.

Register.jsx

Cadastro de nome, email e senha. Depois do sucesso, o usuário já entra logado.

Dashboard.jsx

Cards de totais (consoles, jogos, gasto, valor estimado) e gráficos Recharts (jogos por console e por gênero).

Consoles.jsx

Lista em cards, filtros, abrir modal de criar/editar e confirmar exclusão.

Games.jsx

Lista de jogos com capa, filtros múltiplos, badge “Digital” e os mesmos fluxos de editar/excluir.

Achievements.jsx

Grade de conquistas locked/unlocked e botões para grant/revoke (útil na apresentação).

Quiz.jsx

Mostra as 5 perguntas, envia respostas, tela de resultado e o botão Resetar quiz (demo) que gera outro conjunto.

15. Pasta frontend/src/components/

Para que serve esta pasta? Pedaços de UI reutilizados em mais de uma tela, ou blocos grandes demais para deixar misturados na page (modais).

Navbar.jsx

Barra superior: links (Dashboard, Consoles, Jogos, Conquistas, Quiz), nome do usuário e logout.

PrivateRoute.jsx

Se não estiver logado, manda para /login. Enquanto carrega o usuário, mostra “Carregando…”.

ConsoleFormModal.jsx

Modal criar/editar console (selects do catálogo). Depois de salvar, dispara toast de conquista.

GameFormModal.jsx

Modal criar/editar jogo: busca autocomplete, gêneros múltiplos, checkbox Versão digital, preços, sinopse. Também dispara conquistas.

A confirmação de exclusão de jogos/consoles pode viver junto da page (há um modal de delete usado em Games/Consoles). O importante: a page orquestra; o modal desenha o formulário.

16. Pasta frontend/src/context/

Para que serve esta pasta? Estado global do React (Context API). Evita passar token e toasts de pai para filho em toda a árvore.

AuthContext.jsx

Guarda user, token (localStorage), login, register, logout e recarrega o usuário via /auth/me.

AchievementToastContext.jsx

Função notifyAchievements: toca o som e empilha toasts no canto superior direito.

17. Pasta frontend/src/services/

Para que serve esta pasta? Comunicação com a API. Isola o Axios para as pages não repetirem URL e header.

api.js

Axios com baseURL: http://localhost:3000/api e interceptor que injeta o Bearer token em todo request.

18. Pasta frontend/src/constants/

Para que serve esta pasta? Listas fixas (não mudam com o banco). Centralizar evita digitação diferente em cada select.

catalog.js

Arrays MANUFACTURERS, MEDIA_TYPES e CONSOLES usados nos formulários e filtros.

19. Pasta frontend/src/utils/

Para que serve esta pasta? Funções auxiliares da interface, sem JSX.

achievementSound.js

Gera o “bling” de conquista com Web Audio API (osciladores), sem arquivo MP3.

Como as pastas conversam (um clique)

Tela (pages/) 
  → api.js coloca o JWT
  → routes/ escolhe o controller
  → middleware confirma o usuário
  → controller valida e chama service/Prisma
  → PostgreSQL grava
  → JSON volta
  → page atualiza a lista / toast
