1. Organização do back-end ~3 min

Fale: “Separei o backend em camadas: rotas só encaminham, controllers atendem o HTTP, services guardam regras reaproveitáveis, e o Prisma fala com o PostgreSQL.”

1.1 Schema de dados

Mostre: backend/prisma/schema.prisma
  • User — conta (email único, senha hasheada)
  • Console — hardware da coleção, ligado ao userId
  • Game — jogo com genres[], consoleName, isDigital
  • Achievement + UserAchievement — catálogo e desbloqueios
  • DailyQuiz — um quiz por usuário por dia
Fale: “Todo dado sensível à coleção é isolado por usuário. Um id de outro usuário responde 404.”

1.2 Controllers

Mostre a pasta: backend/src/controllers/
ArquivoResponsabilidade
authController.jsregister, login, me
consoleController.jsCRUD de consoles + conquistas no create
gameController.jsCRUD de jogos + isDigital + conquistas
dashboardController.jsestatísticas agregadas
achievementController.jslistar / grant / revoke (demo)
quizController.jstoday, submit, reset
externalGameController.jsbusca catálogo + RAWG + Steam
Fale: “O controller valida entrada, chama Prisma/service e devolve status HTTP + JSON.”

1.3 Rotas

Mostre: backend/src/app.js e a pasta routes/

Fale: “As routes só mapeiam URL → função. Quase todas passam pelo authMiddleware, que valida o JWT e coloca req.userId.”

2. Teste da aplicação (Swagger) ~2–3 min

Equivalente do roteiro: “ferramenta de teste de APIs” → Swagger UI.
Faça ao vivo:
  1. Abra http://localhost:3000/api-docs
  2. POST /api/auth/login (ou register) → copie o token
  3. Botão Authorize → cole só o token
  4. GET /api/auth/me → 200
  5. Mostre 1 rota protegida sem token (logout do Authorize) → 401
  6. Autorize de novo e execute um GET de consoles/jogos
Fale: “Com o Swagger eu documento e testo a API sem depender do frontend. O cadeado indica rota protegida por JWT.”
Guia detalhado: docs/SMAUG-Como-Testar-Swagger.pdf

3. Front-end ~2 min

3.1 Tecnologia

  • React 19 + Vite (SPA)
  • React Router para páginas
  • Tailwind CSS para estilo
  • Axios para a API (interceptor JWT)
  • Recharts no Dashboard

3.2 Organização do código

frontend/src/
  pages/        → telas (Login, Games, Quiz…)
  components/   → Navbar, PrivateRoute, modais
  context/      → Auth + toast de conquistas
  services/     → api.js (Axios)
  constants/    → catálogo de consoles/fabricantes
  utils/        → som da conquista
Fale: “Pages orquestram a tela; components reutilizam UI; contexts guardam estado global de login e notificações.”
Mostre: App.jsx com rotas públicas vs PrivateRoute.

4. Ideia de agendamento na interface ~1–1,5 min

No roteiro: “explique como foi a sua ideia de agendamento”.
No SMAUG: o “agendamento” é o Quiz Diário.
Fale: “Cada usuário tem um quiz por dia. O backend define o ‘hoje’ em UTC (getTodayUtcRange em quizService.js). Se já existe registro do dia, reaproveita; senão cria 5 perguntas sorteadas. Na interface mostro o quiz do dia e o resultado; para a apresentação há o botão Resetar quiz (demo), que gera outro conjunto na hora.”
Mostre: tela /quiz + trecho de getTodayUtcRange.

5. Demonstração: criar um console ~1–1,5 min

Equivalente a “criar uma campanha”.
Faça:
  1. Entre logado → menu Consoles
  2. Novo console → preencha nome, fabricante, geração, mídia, preços, nota
  3. Salve
  4. Aponte o card na lista
  5. Se for o primeiro console, mostre o toast de conquista + som
Fale: “A criação dispara o backend, grava no PostgreSQL e pode desbloquear conquista. A resposta traz unlockedAchievements e o frontend notifica.”

6. Demonstração: criar um jogo ~1,5–2 min

Equivalente a “criar uma aposta”.
Faça:
  1. Menu Jogos → Novo
  2. Busque “zelda” (ou outro clássico) no autocomplete
  3. Selecione → veja nome, console, gêneros e sinopse preenchidos
  4. Marque ou não Versão digital
  5. Complete preços/nota → Salvar
  6. Mostre o card com “· Digital” se marcou
Fale: “O jogo pode existir mesmo sem o console físico cadastrado. A busca prioriza clássicos de console e tem fallback se a RAWG estiver fora.”

7. Resultado (quiz / conquistas / dashboard) ~1,5 min

Equivalente a “comportamento do resultado de uma campanha”.
Faça uma destas demos (ou as duas se der tempo):
  1. Quiz: responda as 5 perguntas → tela de resultado X/5 → se gabaritar, conquista QUIZ_MASTER
  2. Dashboard: mostre totais e gráficos atualizados após os cadastros
  3. Conquistas: mostre locked/unlocked na página Conquistas
Fale: “O resultado não é só um número: a interface mostra feedback visual, e o sistema pode liberar conquista com notificação estilo console.”

8. Deslogar e tentar rotas protegidas ~1 min

Faça:
  1. Clique em Sair na Navbar
  2. Tente abrir manualmente http://localhost:5173/, /games, /quiz
  3. Mostre o redirecionamento para /login (PrivateRoute)
  4. (Opcional no Swagger) remova o Authorize e chame GET /api/games → 401
Fale: “No frontend o PrivateRoute bloqueia a UI. No backend o middleware bloqueia a API mesmo se alguém chamar direto.”

9. Perfil de usuários ~1 min

O que existe hoje no SMAUG: fluxo completo de conta, sem tela “editar perfil” dedicada.
Mostre:
  • Tela de Register e Login
  • Nome do usuário na Navbar após login
  • No Swagger: GET /api/auth/me devolvendo id, name, email, createdAt
  • Isolamento: cada usuário só vê a própria coleção
Fale: “O perfil autenticado fica no AuthContext. A senha nunca volta nas respostas. Como melhoria futura, dá para criar uma página de edição de nome/senha.”

10. Esquema de mensagens de sucesso e erro ~1 min

TipoOnde apareceExemplo
Erro de formulário / API Banner vermelho nas pages/modais “Credenciais inválidas”, “Campos obrigatórios ausentes”
Erro de validação local Antes de enviar “Adicione pelo menos um gênero”
Sucesso de conquista Toast canto superior direito + som “Conquista desbloqueada”
Mensagem admin (conquistas) Texto de feedback na página grant / limpar conquistas
Resultado de quiz Card verde + acertos/erros por pergunta “Você acertou X/5”
Backend JSON { error: "..." } + status HTTP 400, 401, 404, 409, 500
Fale: “Padronizei erros no backend com campo error. O frontend lê err.response.data.error e mostra na interface.”

11. Demonstração forçando erro ~1 min

Escolha 1 ou 2 ao vivo (fáceis e claros):
  1. Login errado: senha inválida → banner vermelho “Credenciais inválidas”
  2. Register duplicado: mesmo email → 409 “Email já cadastrado”
  3. Jogo sem gênero: tentar salvar sem adicionar gênero → erro local
  4. API sem token: Swagger sem Authorize em GET /api/games → 401
  5. Quiz já respondido: submit de novo sem reset → 400
Evite derrubar o PostgreSQL na apresentação. Prefira erro de negócio/validação.

12. Pontos fortes e pontos a melhorar ~1–2 min

Pontos fortes

  • Arquitetura clara: routes → controllers → services → Prisma
  • Segurança básica sólida: bcrypt, JWT, isolamento por userId, rotas privadas
  • Experiência “gamer”: conquistas com toast + som
  • Quiz diário com variação de perguntas e reset para demo
  • Autocomplete de jogos com catálogo de console + fallback externo
  • Swagger documentando e permitindo testar a API
  • Dashboard com métricas reais da coleção

Pontos a melhorar

  • Página dedicada de perfil (editar nome/senha, avatar)
  • Upload real de imagens (hoje usa URL)
  • Testes automatizados (unit/integration) além do Swagger manual
  • Deploy em nuvem (API + banco + frontend)
  • Paginação e busca textual nas listas grandes
  • Timezone configurável no quiz (hoje usa UTC)
  • Mais conquistas e perguntas dinâmicas por dificuldade
Frase de fechamento: “O SMAUG entrega um CRUD autenticado completo, com diferenciais de conquistas, quiz diário e integração de busca — e ainda deixa caminho claro para evoluir perfil, mídia e deploy.”

Ordem sugerida no dia da banca

  1. Abrir frontend logado + Swagger em abas separadas
  2. Falar backend (schema → controllers → routes → libs) apontando pastas
  3. Swagger: login + Authorize + 1 GET protegido
  4. Frontend: estrutura + PrivateRoute
  5. Quiz (agendamento) em 30–40s
  6. Criar console → criar jogo → ver dashboard/conquista
  7. Logout → tentar /games → login de novo ou 401 no Swagger
  8. Forçar 1 erro → falar mensagens
  9. Fechar com fortes/melhorias

  • ☐ Conta de demo criada
